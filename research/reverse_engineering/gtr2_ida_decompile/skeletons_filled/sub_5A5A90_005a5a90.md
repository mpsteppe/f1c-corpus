## sub_5A5A90_005a5a90 — queue drain: dequeue+dispatch items, free second list

**Summary:** Mutex-guarded queue processing routine: spins popping nodes from the queue at this+0x554 (clearing each node's byte flag) and dispatching every non-null payload through the virtual method at vtable+0x5C; then drains the second mutex-guarded list at this+0x5A8, unlinking and freeing nodes plus their flag-marked payloads. Part of an asynchronous item-queue/worker system.

**Written-by note (persistence):**
- *(this+0x554) 0x8: written per dequeued node each call (cleared to 0 right before the pop); a poke to this field on a queued node is transient and overwritten when that node is drained.
- *(this+0x5A8) 0x4: node link fields rewritten during the unlink walk whenever cleanup runs; recalculated state, a poke would be overwritten on the next drain.
- this 0x5A8: head pointer mutated whenever nodes are removed; recalculated/consumed on every call — an external poke would be overwritten by the next drain.
- this 0x5AC: auxiliary link updated on removal; recalculated state, poke would not survive a drain.
- this 0x5B0: tail pointer updated on removal; recalculated state, poke would not survive a drain.

**Guard interpretation:** Second list: cleanup only starts if the mutex handle at 0x5B8 is non-null and WaitForSingleObject on it returns 0 or 128; then the loop passes while count (0x5B4) > 0 and both the head pointer (0x5A8) and the head node's payload are non-null — each passing iteration unlinks and frees one node (and its payload if the node flag byte is set). It is BLOCKED and exits when count <= 0, the head is null, the payload is null, or the mutex wait returns anything other than 0/128 (then v9 = 0 and the loop is not entered). First queue: each iteration passes only if a mutex handle exists at 0x564, the pop (sub_59F9F0) succeeds, and the popped payload is non-null; otherwise the loop breaks without dispatching.
