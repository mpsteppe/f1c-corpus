## sub_5FD150_005fd150 — Flush dirty data block into locked buffer

**Summary:** Dirty-block flush: when the object holds items (count at this+0x30 nonzero) and the 0x80000 dirty flag is set, it locks the first buffer via sub_5FCA00, bulk-copies the whole data area — (this[0x24] * this[0x2C]) << 6 bytes from this+0x60 to the locked pointer at this+0x44 — unlocks via sub_5FCA80, and clears 0x80000; it then finishes with the manager vtable+424 call. If the count is zero, that value is returned immediately.

**Called by:** sub_5FDB90 (005fdb90)

|------|--------|-----|------------------------|---------|
| this | 0x0 | RW | — | Flag word: 0x80000 (dirty/needs flush) read as gate and cleared after the flush |
| this | 0x24 | R | — | Element size factor (this[9]) in the copy length (this[9] * this[11]) << 6 |
| this | 0x2C | R | — | Capacity/size factor (this[11]) in the copy length |

| this | 0x60 | R | — | Source data base (this[24]) for the bulk copy |

**Written-by note (persistence):**
- this 0x0: bit 0x80000 is conditionally AND-cleared after a successful flush (lock + non-null destination); it is never set here. An external poke setting 0x80000 triggers a full re-flush on the next call; other bits are read-only here.

**Guard conditions:** Early out when the count at this+0x30 is 0 — the function returns that 0 and does nothing else. BLOCKED unless `(*this & 0x80000) != 0` (dirty flag set): without it no copy of any kind happens, though the manager call (vtable+424) still runs whenever the count is nonzero. Inside the dirty path, the copy and clear depend on sub_5FCA00 and on this+0x44 being non-null — if the locked pointer is null the function returns early (no copy, no unlock, dirty flag kept). When the pointer is valid: qmemcpy, sub_5FCA80 unlock, then 0x80000 is cleared.
