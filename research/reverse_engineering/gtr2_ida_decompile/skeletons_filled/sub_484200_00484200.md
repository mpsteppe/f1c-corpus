## sub_484200_00484200 — ProcessUiMessageQueue

**Summary:** Drains a mutex-protected linked list of queued UI messages: dispatches message types 1/2/4 to set the object's UI state code at offset 0x364 and enable/disable dialog controls (IDs 1005 and 1185), then (under a second mutex) refreshes the window title via StringCopyWithBufferRealloc. Part of the game's Windows dialog/message-pump layer.

**Called by:** sub_489700 (00489700)

**Struct fields accessed:**

| Base | Offset | R/W | Init (literal → value) | Purpose |
|------|--------|-----|------------------------|---------|
| this | 0x364 | RW | 4 | UI state code: set to 1/2/4 depending on processed message type |

**Written-by note (persistence):**
- this 0x364: conditional write, event-driven — each processed message stores 1, 2, or 4 (or forwards to sub_4839A0 if already nonzero). Not recalculated every frame, but an external poke will be overwritten the next time a matching queued message is dispatched.

**Guard conditions:** Queue processing is gated on mutex acquisition: `hHandle != 0` and `WaitForSingleObject == 0 || == 128` selects the queue head; otherwise v3 = 0 (no messages read). Inside the loop, only message types 1, 2 and 4 act: type 1 → state `this[0x364] = 4` and `EnableWindow(GetDlgItem(hDlg,1005), 0)`; type 2 → state = 2 and `EnableWindow(GetDlgItem(hDlg,1185), 0)`; type 4 → if `this[0x364]` is already nonzero, calls sub_4839A0, else sets state = 1; any other type is skipped (list simply advances). After the loop, `sub_47FAA0(this,1)` runs only if `v3[3] > 0`. The window-title copy runs only when the resolved string (queue entry, else WindowName) has `strlen != 0`.
