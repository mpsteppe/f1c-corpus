# MAS mark-prunable wrapper static review

Scope: `0x0053CE10`, isolated as a one-function packet after its MAS root-loader dependency was promoted. This review is static evidence only; it makes no runtime, ownership, or ABI-reviewed claim.

The recovered wrapper forwards its two arguments to `0x0053CBC0` and returns that result unchanged. Only when the result is zero and the output-slot pointer itself is non-null does it dereference the loaded pointer and OR `0x8` into the dword at object offset `0x114`. This is a read-modify-write, so all other flag bits are preserved. A failed root load or null output-slot pointer causes no wrapper flag write.

The lifecycle name is supported by cross-function static evidence rather than the wrapper body alone. Its sole caller, `0x0055B200`, invokes it for a parsed scene `masfile` directive. The sole caller of bulk-prune function `0x0053CED0` is `0x00543FA0`, which calls the prune routine after successful vertex-buffer/resource setup and immediately before its final state update and zero return. The common bit-3 test therefore supports the conservative label `mark_for_post_setup_prune`; it does not establish a concrete class name or runtime-verified policy.

The original success path has an important safety precondition. The root loader contract records zero returns for null, empty, and unrecognized-header inputs, paths that do not necessarily establish a non-null loaded pointer. The wrapper checks `output`, not `*output`, before writing through `(*output)+0x114`. A non-null output slot combined with a zero root result is therefore safe only when `*output` is already a valid loaded object. The raw scene-parser decompilation declares its local output slot without showing initialization before this call, so caller initialization remains unresolved until instruction-level evidence is obtained. A replacement must define this case explicitly rather than reproduce an unchecked dereference by accident.

All three independent candidates validated after worker output had fully flushed. Their differences were naming, formatting, redundant offset-zero layouts, and lifecycle prose; none changed the recovered branch, return propagation, or flag write. The reconciled record removes the synthetic pointer-slot layout, retains only the directly accessed object offset, and keeps concrete type, ownership, threading, ABI, and runtime behavior unresolved.
